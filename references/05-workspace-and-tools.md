# 工作区、工具与流程约定

## 1. 工作区（`<工作区>`）

| 用途 | 位置 |
|---|---|
| **工作缓冲**（解包目录、`_src_*` / `_work_*`、探查脚本） | 工作区根 |
| **提取结果**（成品 txt + 解析报告同放） | `提取结果/` |
| **定稿脚本**（跨作复用） | `scripts/` 顶层 |
| **探查脚本归档** | `scripts/_archive/<game>/` |
| **通用品检** | `scripts/check_text.py` |
| **探查 / 识别 / 体检** | `scripts/probe.py`（限量探查）· `scripts/identify.py`（容器→引擎）· `scripts/memcheck.py`（体积体检） |
| 用户自建汇总库 | `<你的成品汇总库>/` |
| 清理记录 | `清理记录_YYYY-MM-DD.txt`（追加式：删/归档/保留/重跑步骤） |
| **项目记忆** | `.workbuddy/memory/`（见 §5 的**两级结构**） |
| 重构前原件备份 | `_archive_restructure_YYYY-MM-DD/`（用户确认后可整体删） |

**源母本**多在 `<原始 dump 目录>/`。脚本路径约定：走环境变量（`VNTRANS_HOME` / `VN_OUTDIR` / `SEVENZ` /
`PROD_KEYS` / `ZRIF` / `PSVDEC`），**不硬编码绝对路径**。

**并行 agent**：本工作区可能同时有别的 agent 在跑 → 覆盖 `scripts/` 或重跑前先看产物 mtime 与内容。

## 2. 常用脚本形态

- `*_extract.py` — 容器 → 消息列表 → txt（一作/一引擎一张表）
- `*_decrypt.py` — 解密/解压（区间键模型 + 定值复元表）
- `*_fix.py` — 定值复元表（`REKEY` / `OVERRIDES` / `TEXT_PATCH` + `apply_fix()`）
- `check_text.py` — 交付前自检（见 `04-verify-and-report.md`）
- **`probe.py`** — **首选**探查器：`magic / entropy / strings / jp / hex / u32 / find / tree`，
  **所有命令默认限量（≤80 行）**。**不要**再写「打印整表/全量正则」的一次性脚本。
- `identify.py` — 一眼判定容器/引擎 + 给出**下一条命令**与**该读哪份 `engines/<slug>.md`**
- `renderfont.py` + 字库 — 从字形图集（GXT/G1T 等）渲染指定槽位，**读图核对**
- 消息中间件 `.pkl` — 解容器与出 txt 解耦，便于反复调行粒度

## 3. 标准流程（S0〜S8 速查；规范正文以 `SKILL.md` §2 为准）

| 步 | 做什么 | 关键判据 |
|---|---|---|
| **S0 识别** | `scripts/identify.py <文件或目录>` | 一次拿到「引擎 + 命令 + 文档」，别反复 hexdump 猜 |
| **S1 源** | 定位母本；`7z l` 看结构 | 头部加密？密码在同目录小 txt；**同捆更新程序先解** |
| **S2 容器** | 解外层，拿脚本资源 | 先 `identify.py`；`XP3`/`CPK`/`PFS`/`NCA`/`PSARC`/`NSAC`/`AFS`/`ROM2`/`DATA.BIN`… |
| **S3 解密** | 还原文件内容 | ① 已知魔数反推键 → ② 字符似然模型 → ③ 定值复元表 |
| **S4 脚本结构** | 认容器与记录格式 | 「文本记录驱动扫描」自定界 ⇒ 永不失步 |
| **S5 文本解码** | 码表 / 替换槽 / 宏 | 假名块先定；替换槽不信 cp932 |
| **S6 提取成行** | 按输出规范落地 | 续写形态**全集**（`03d-extract-lines.md` B1） |
| **S7 自检 + 报告** | 自检 + 写报告 | 报告必须含**重跑步骤** |
| **S8 收尾** | **`SKILL.md` §6 固定动作** | `memcheck.py` ＋ 落记忆；**不等用户提醒** |

## 5. 记忆维护（**两级结构：小主索引 + 按类子文件**）

```
.workbuddy/memory/
  MEMORY.md      ← 自动注入！只放 目录约定 + 铁律 + 导航；>8 KB 就是该拆了
  WORKS.md       ← 作品索引（新作只追加一行）
  ENGINES.md     ← 引擎路由表（一句话索引 + 「详见」列）
  engines/*.md   ← 一引擎一文件，自包含（单个 ≤10 KB）
  works/*.md     ← **可选层**：仅当某作结论 > 5 KB 才开（日志只留一行指针）
  TOOLS.md       ← scripts/ 工具索引
  YYYY-MM-DD.md  ← 当日流水（append-only）；**每作写一个 `## 作品名` 小节**，查历史先 Grep ⬅ 主力
```

- **规则**：`.md > 10 KB` ⇒ **按主题拆**（`SKILL.md` 例外：唯一必读文件，上限 **12 KB**）；
  `MEMORY.md > 8 KB` ⇒ 必须拆。**主动做，不等用户提**（`memcheck.py` 兜底）。
- **每作收尾**（S8，`SKILL.md` §6）：跑 `python scripts/memcheck.py` → 有新作/新引擎/新脚本就落位 →
  新坑写进 `references/03?` 并在 `SKILL.md` §3 索引补一条。
- **查历史**：先 `Grep <作品名|引擎名>` `.workbuddy/memory/`，**只读命中段**，不整读日志/报告。
- **用户说「清理产物」时**：① 按约定清理；② **顺手检查本 skill 是否需要修订/补充**。

## 6. 上下文卫生（**核心纪律**；不是为了省 token，是为了不降智）

> **上下文是有限资源，且会被稀释**：塞进来的无关内容越多，真正相关的信号越被挤到边缘，
> 推理质量与速度都会掉。**每一次读文件、每一次跑脚本，都等于往上下文里写东西 —— 按「值不值得」来。**
> 这里的「上下文」包括：① 自动注入的记忆文件；② 你 Read 的文件；③ **脚本/命令的 print 输出**（最容易失控的一项）。

**7 条铁律**

1. **输出即上下文 —— 探查脚本一律限量**：首选 `scripts/probe.py`（默认 ≤80 行，`--top`/`--len` 调）。
   **永不** `xxd` 整文件、**永不**正则/整表 dump、**永不**为了「看一眼」打印几千行。
   > 实证（鳥籠のマリアージュ）：一次 `%\x00` 全量扫描打印 ~100 KB，**信息量 ≈ 0**，
   > 却把当轮上下文挤掉大半 —— 之后判断明显变钝（本该 1 次调用定案，拖成好几轮）。
2. **只读「当前这一步」需要的**：动手前只读 `SKILL.md`；进入某阶段才读那一份 `references/03?`；
   定位到引擎才读那一份 `engines/<slug>.md`。**不要为了"保险"预读**（§3 索引已覆盖全部坑）。
3. **长会话要「卸货」**：中途结论（字节布局、密钥、记录格式）立刻写进
   `_work_<game>/NOTES.md` 或 `.workbuddy/memory/works/<slug>.md`，**需要时再读回来**；
   不要靠「记在脑子里」硬扛 —— 上下文一长，早先的结论会被冲淡、开始自我重复。
4. **同一事实只存一处**：写记忆前先 `Grep` 是否已有；重复=每次都被加载两遍。
   （主索引只放铁律+导航，细节一律下沉。）
5. **大二进制不进上下文**：一律脚本摘要（`probe.py magic/entropy/tree`），要字节才 `hex` 小窗口。
6. **不读成品/日志全文**：判定用 `check_text.py`，抽查用 `sed -n 'a,bp'`；查历史先 `Grep` 再只读命中段。
7. **看见大文件就拆，不等用户提**：`.md > 10 KB` ⇒ 按主题拆（`SKILL.md` 上限 12 KB）；`MEMORY.md > 8 KB` ⇒ 必须拆。
   兜底：每作收尾跑 `python scripts/memcheck.py`（退出码 1 = 有待处理）。

**换算参考**：Read 一个 10 KB 的 md ≈ 往上下文写 ~4k token 的杂质；一次不限量的 print 可以写进 25k+。
**先问：这段内容，是这一步做决定必需的吗？** 不是就去 `Grep` 定位 or 干脆不读。

## 7. 决策纪律 —— 防「钻牛角尖 / 做无用功」（**最高优先级**）

> 症状：像没规划、反复试错、一耗半小时、token 烧得凶。
> **根因只有一个：没先立「假设 ＋ 证伪条件」就动手**，于是每跑一次都不知道自己在验什么、错了也停不下来。
> **铁律：写不出「这一步能证伪什么、跑完如何改变判断」的探查，不许跑。**

**A. 开工先写「做题卡」**（`_work_<game>/NOTES.md` 顶部，1 分钟，3 行）
1. **目标** —— 一句话：交付什么。
2. **不确定点清单**（按风险倒序）—— 每点标出**候选钥匙**：已知明文 / 外部资料 / 参考实现 / 结构线索。
3. **当前唯一在跑的假设** ＋ 它的**证伪条件**（用哪个已知串/哪条判据能一击否定）。

**B. 先找齐钥匙，再动手** —— 解码/解密前先列「**一定能读出的东西**」：
系统消息、选项/菜单、外部对照源（vndb / 官方站）、同作平行语、已知魔数、参考实现。
> 钥匙常常**早就在手边**：BELIEVER! 的锚定明文一直躺在 `dialog_common.hesexe` 的系统消息里。

**C. 停滞判据（硬闸门，不许商量）**
- 同一假设上**连续 2 次探查没有减少不确定性**（没产出新的可判定信息）⇒ **强制停手**，回 A 换假设/换钥匙。
- **禁止在同一假设上继续加码**（「再来一次可能就对了」＝典型钻牛角尖）。
- 单一子问题**超过 3 次探查未收敛** ⇒ **停下向用户汇报**：当前假设 / 已排除什么 / 下一步建议。**不许自己硬扛。**

**D. 工具优先序（永远从上往下，不许跳级）**
① 现成参考实现/专用工具（**先确认是同一作/同一变体**）→ ② **已知明文锚定** → ③ 结构推理（魔数/长度/单调性/对齐）
→ ④ 确定性表 / 定值复元表 → ⑤ 枚举（**仅当 ①②③④ 全否，且已向用户确认**；见 `SKILL.md` §0 ①）。

**E. 每次探查只写一行台账**：`假设 → 判据 → 一条最小命令 → 结果如何改变判断`。
写不出这行 ⇒ 这次探查就是无用功，**不要跑**。（写完发现判据模棱两可 ⇒ 也先停，把判据定死再跑。）

**F. 预算是硬约束**：探查＝**分钟级**。单次探查 **>2 分钟**、或**输出 >80 行**、或**要写 >50 行一次性脚本**
⇒ 基本是方向错了，先停并按 C 处理。
