## C. 交付层（每次必查）

**C1. 主角名 / 称呼宏被当空控制码丢掉**
主角可改名 ⇒ 脚本里**必然存在**插入宏。已见：遥か3（`5d 17 00` 静默前缀 + `5b XX 00` 称呼表；
`0x16`=将臣くん…）、はかれなはーと（`f.name`/`f.family`）、ひめひび（`0x0c02`/`0x1802`）、
花宵（`FFE6`/`FFE7`）、カレイドイヴ。
→ 交付前**主角名出现性自检**（`check_text.py --name X`）。默认名从 eboot 名字输入初始值表 / Config 取。
→ 出现次数还要与被称呼的台词量**量级相符**。**若脚本内无任何改名机制 ⇒ 主角为固定名**，直接用其出现次数核对。
→ ★★ **「人名宏」与「称号」必须分开判 —— 判据＝同句共现**（千銃士R 实证）：`<player>`(4,932 处) 与「マスター」**同句共现**
（`マスターである<player>でも`／`さすがマスター。<player>ちゃんは誤魔化せないな。`）⇒ **`<player>` 是「可改名的人名」**，
**绝不能填「マスター」**（会得到 `マスター君`／`マスターちゃん` 这类错译）。同作还并存 `<fpp>`(第一人称 私/僕/俺/自分)、
`<birthday>` ⇒ **玩家侧变量宏常成族出现**，先按「同句共现 / 是否可替换成同一词」逐个定性再填值。
→ ★ **无默认名时的口径**：穷举 Master 全表（本例 172 张 `*MasterVO.bin`）+ IL2CPP `global-metadata` + Unity 基础 asset
均无默认名 ⇒ 按 `05-selfcheck.md` C6 **留全角占位 `〔主人公名〕`**（不猜测、且过品检），并在报告 §重跑步骤给「改一行常量即可重生成」的说明。

**C2. 选项文本整块漏掉**
被当 `[...]` 标签丢弃。→ 专门提取 `[seladd/_link/_click/_extmenu/_homepage … text="…"]`，一行一条。
⚠️ **注音正则必须限定基底语**（`[漢字'よみ]` 的基底不含 `= " '` 与空白），
否则 `[seladd text="X" target="*sel_1" cond='f.shiba==false']` 会被误当注音，
**把命令残骸当正文**输出（蝶の毒实证）。
⚠️ **注音不止一种写法**：HuneX 系作 **`<読み>基底語|`**（読み写在 `<>`、基底语紧随、以 `|` 收尾）——
上屏显示的是**基底语**（読み为振り仮名），须还原为基底语（`ここ<しらきまち>白葵町|に` → `ここ白葵町に`），
否则正文残留 `<`・`|`（円環のメモーリア实证；全作仅 1 处）。
⚠️ 同理，**孤立 ASCII 残留**（半角标点 `､`/`｡`＝字节 0xA4/0xA1、多余 `」`、孤立 `\`）先照**原始字节**判
「原文笔误 vs 提取缺陷」，属笔误者用**整行定值表**修并报告单列（円環のメモーリア：3 处）。

**C3. 说话人前缀残留的 4 种形态**
1. 独立名字札行 `【秀雄】`（含原作笔误 `!【警官２】`）→ 丢弃该行
2. 行首 `【名】` + 正文 → 去掉前缀
3. 行首 `名前：` / `名前「` → 去掉前缀
4. 大字号演出写进正文流的裸名行（见 B5）

**C4. 系统 / UI 文本混进正文**
`sysscn/`・`main/`・config/help/save 类 → 不收、也不产出「系统・UI テキスト」附属文件。

**C5. 行数 / 长度异常时先查合并逻辑**
不要急着怀疑源。（コルダ 最长行 152 字 / ときたま 589 字都是合并 bug。）

**C6. 未解码位占位符不得用 `〓`(U+3013)**
`05-selfcheck.md` §1 自检把 `〓` 判 **E**（历史遗留占位符）。要「留占位符（不猜测）」同时过品检 ⇒ 用全角括号式
**`〔未解析〕`**（遥か5 实证，运行时变量 12 处）。仍须在报告里**单列未解析码位**。

**C7. 用「尾部固定签名」批量给载体分类，别逐条启发式**
同一作里 **载体用途不同、尾部签名不同**：遥か5 实证
`CLOSE + C7 + 1e 5e9008d3` = 用語辞典解説文；`CLOSE + M91 + 1e 5e9008d3` = 系统/UI（整体排除）。
→ 先按签名把 leaf/文件**分成 剧本 / 辞典 / 系统UI** 三堆，再各自处理；
比「关键字黑名单逐条过滤」稳得多（系统/UI 会以零散长句混进正文，关键字扫不干净）。

**C8. 「用語辞典 / 术语表」载体可能是同发行商他作的遗留串 —— 先读内容再决定收不收**
Otomate 系常见：`SYSTEM.cpk/DATABASE/dbDictionary.gbin`、`strGame.gstr` 等**按模板复用**，里面装的却是**他作**数据。
- Norn9 Act Tune 实证：`dbDictionary.gbin`（39 KB）整表是 **薄桜鬼** 术语（`会沢正志斎`/`新選組`/`幕末`/`藩士`…），
  **无一条本作词条** ⇒ **整体排除，本作无用語辞典可并入**。
- 判据：抽 3–5 条看是否与**本作角色/世界观**相关（本作关键词 `ノルン`/`能力者`/`空汰`/三名女主 → 命中 0 即遗留）。
- 与 A4（eboot 串表遗留）、铁律 12 同类；**千万别把遗留术语表当本作辞典并入成品**。

**D1. 清理产物只在用户明示「清理产物」时做**；任务收尾**不要**主动清理。

**D10. 用語辞典字段 >1 时的取法（避免把「读音/分类」混进正文）**
辞典表常见**两个解说字段**：一个「一覧用短注」（往往形如 `分类。見出し語。短い説明。`，含**分类与读音**）、
一个「詳細解説」（纯解说正文）。按 §0「一行一条、**不带读音**」⇒ **取詳細解説字段**，不取短注字段（其 `分类。見出し語。` 即读音/注记）。
落地：`【見出し語】詳細解説`（条内换行合并）。实测（爽海バッカニアーズ! `dic.csv` f6）：51 条，取 f6 后无冗余名反复、行宽正常。

## A12. 「主角名检索不到」有两种，必须先判别（`pitfalls/A1-decode-core.md` 交付层 ① 的补充）

成品里搜不到主角名时，**别立刻断言「名字宏被当空码丢弃」** —— 先数**正文里的特殊码**：

- **情形① 名牌名（正常）**：名字**只**出现在说话人名牌（独立记录），正文里既无名字也**无任何宏**。
  ⇒ 成品无此名**属口径正常**（不加说话人前缀），**不是缺陷**。判据＝**正文特殊码 0 个**。
  BELIEVER! 实证：`園崎みあ`（女主，vndb c40222）在 `op 0x1a` 名牌出现 **4,476** 次（全角色最多），
  而正文 13,632 段里特殊码 **0** 个、`崎`/`みあ`/`園崎` **0** 次（仅 3 个「園」＝公園/学園）。
- **情形② 内联宏被丢（缺陷）**：正文里存在特殊码（`0xFFFC`/`0xFFFF`/`0x8000+X`…）落在
  「他人称呼主角」的句位 ⇒ 那是名字槽，须替换为**外部定名**（否则留占位）。
- **判别顺序**：先数正文特殊码 → 有则②、无则①。**别一搜不到就断言「宏被丢弃」。**
- ⚠ **主角「可改名」必须以证据判定**（eboot 名字输入初始值表 / 名牌串是否为变量或含宏），
  **不要凭「乙女游戏通常可改名」假定** —— BELIEVER! 就误判过「可改名」，实为**定字面名**（名牌串
  是字面 `園崎〈0x8000〉みあ`，非变量）。
