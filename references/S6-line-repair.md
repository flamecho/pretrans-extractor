# 行完整性修补（实战案例）

> 本册专收**修补事故与判据**：joinup 假闭合、双版两条记录、`配平` 三次造成损害。
> 探针与六类缺陷流程在 `S6-line-integrity.md`。

## ★★ 修补工具的 `joinup` 判据必须验「上一行确实未闭合」（2026-10-27 实证）

**事故**：`fix_wrap_pairs` 的 `joinup` 写成「上一行**闭符号数 ≥ 开符号数**（即平衡）也并入」，
于是「无引号地の文 + 独立括弧段」被并成一行。テミラーナ成品 L23795 由 3 条记录并成 147 字：

```
[23762] 話している間にも、…また冷たい彼に戻ってしまった。
[23763] 相変わらず寝不足も続いているのか、…イライラしているようにも見える。
[23764] （早く根本的な原因を突き止めないと。…何の違いがあるの？」   ← 开「（」用「」」收（源侧笔误）
         ↓ joinup 触发两次
147 字一行（`」` 还被 trim 删掉 ⇒ 括号失衡）
```

**正确判据**：`out[-1].count(op) > out[-1].count(cl)`（上一行**开>闭**，确实未闭合）才并入。
写成 `cl >= op` ⇒ 上一行平衡时也并 ⇒ **必错**。

**为什么这类 bug 特别危险**：
1. 误并后**符号反而平衡**（多条句子的引号加起来对得上）⇒ `struct_probe` 的 A/B 失衡查不出来；
2. 唯一线索是「**行明显过长**」——所以要把「最长行 ≫ 第二长行」也作为探针；
3. 它发生在**修补阶段**，源提取本身是对的，重新提取不会自愈。

**验收（三条一起看）**：
```bash
# ① 最长行 vs 第二长行（倍率 ≥1.6 且最长 ≥120 字 ⇒ 疑似单点误并）
# ② 每行 >100 字且含 ≥2 个「。」的条数（配合中位数判断）
# ③ 有源的作：成品逐行与源记录序列做「完全相等 / 拼接」对齐，拼接命中＝误并
```

⚠ 无源的作**不要穷举**：误并后从成品侧不可判，只能标为已知风险并写进报告。

### ★★ 双版是**两条独立记录**时：正确动作是「删一条」，不是「拼成一行」（2026-10-27 ミストニア）

**错法**（我干过的）：

```
源：#10120 （%の仕業か）        ← 点名版
    #10121 （彼女の仕業か」      ← 泛称版
成品：「（アプローズの仕業か）（彼女の仕業か」    ← 两版拼一行 + 硬补一个「
```

后果三连：① 括号失衡（`（`×2 / `）`×1）；② 凭空多出一个 `「`（为配源侧孤零零的 `」`）；
③ 行数比源记录少 1，闭合计不上（35,226 vs 35,227），成为「说不上来的差额」。

**正确动作**：按「点名版／泛称版双写 ⇒ 去泛称留点名」**删掉泛称版那一条记录**，
保留的点名版自身就是完整记录（`（アプローズの仕業か）`）。

**判据**：双版在数据层的两种形态要分开处理 ——

| 形态 | 例 | 动作 |
|---|---|---|
| 两版被缝进**同一条记录/同一行** | ビルシャナ `…なんだ。「俺にとって、遮那王様は…` | 取更完整一版，名字统一（`merge_name_variants`）|
| 两版是**两条独立记录**（各占一次点击） | ミストニア `（%の仕業か）` / `（彼女の仕業か」` | **删一条**（留点名版），**不要合并** |

**自查**：合并后若出现 `（A）（B`、`「` 数量与 `」` 不等、或行数比源记录少，就回头看这条。

### ★★ 「配平括号/引号」不是合并行或增删标点的理由（2026-10-27 もし神様）

某作成品里发现一行 `え……？　きゃっ……。（おでこにエースくんの手が……）冷たくて気持ちいいな`（末尾少 `）`）。
回源：`＠%name%` + `え……？　きゃっ……。` + `<pb>`，接着又一个 `＠%name%` + `（おでこ…）冷たくて気持ちいいな）` + `<pb>`
⇒ **两个文本框**（各有名札、各有 `<pb>`），本该两行。

成因是**一条未登记的「括号配平」后处理**：

| 源侧形态 | 数量 | 那条后处理干了什么 |
|---|---:|---|
| 行首 `（` 比 `）` 多 1（心声跨 `<pb>`，闭括弧在下一块） | 36 | 行尾**补**一个 `）` |
| 行内 `）` 比 `（` 多 1（作者笔误） | 2 | **并入上一行**，再删掉多出的 `）` |

后果三连：① 「一次点击一行」被破坏（两框并一行）；② 凭空删掉 1 个字符；③ 行数比源少 2，闭合计不上。

**硬规则**

- `<pb>` / `<wait>` / `(message-clear)` 之间的**行边界＝点击边界**，任何「整理」都不许跨过它。
- **不许**为了配平而增删 `（）「」『』`；源侧不配平就是作者笔误或跨框心声 ⇒ 登记 [W]。
- 若已经动过：**回源重跑 → 逐行 diff**，命中「成品 = 源 + `）`」或「成品 = 源两行拼一行」就整体回退。
  该作修完 45,061 → 45,063、diff 0 差异、品检 PASS。

### ★★★ 「配平引号」第二次造成损害：连 allow 登记都被它推翻（2026-10-27 十三支演義）

**症状**：成品有一行 `（え！？）「貴様！　我々を侮辱するか！」　もう我慢ならん！！`（30 字），
看着像「心声＋台词＋旁白」粘在一起，**末尾还少了一个 `」`**。

**真相**：源里是**两个框**——

```
sure29:  maintxt_print '（え！？）'   ← 框1
         batch
         thread_change 'sure30'      ← 换线程（一定是另一个框）
sure30:  maintxt_print '「貴様！　我々を侮辱するか！」'
         maintxt_print '　もう我慢ならん！！」'   ← 源侧多打一个 」
         batch
```

**根因不是提取器**，是交付后一条「配平引号」的后处理：它把 6 行源侧不配平改成配平（补 `」`／补 `）`／把 `」` 改 `）`／删多余 `」`），
其中一处顺手把两个框并成一行再删掉收尾 `」`。**而 allow 文件里本来就逐行登记了这 6 行**——改成配平后，allow 反而对不上了。

**判据（发现这类问题的三步）**

1. **重跑 extractor，与成品逐行 diff**：只剩「引号增删 / 跨框合并」⇒ 一定是后处理干的（本次 6 处，1 处并框）；
2. **回源看框界**：`batch` / `thread_change` / `speaker_change` 之间必然是不同框；本例 `thread_change` 直接证明换框；
3. **查 allow**：若成品某行与 allow 登记的形态**不一致**，说明成品被改过，应以 allow＋源为准。

**处置**：撤销后处理，恢复 extractor 直出；6 行源缺陷照源保留、由 `--allow` 豁免。

★ 这是**同一类错误的第二次**（前一次 もし神様：38 行被补/删括号、2 处被并框）。
规律：**「让文本看起来配平」的自动化，一定会同时改标点、跨框合并、并让豁免清单失效**。
正确做法只有一条：**源侧不配平就登记 [W]，一个字都不动**。

⚠ 另一个连带坑：名字宏替换**必须放在成行之后**。若在 `flush()` 里就把 `#Name[1]` 换成 `関羽`，
那些「整框只有一个名字宏」的行原来因「无日文字符」被丢弃，替换后 `関羽` 是日文，会被当成正文捞回来（本作 +88 行）。

### ★★★ 第三次：并框 + 删 `」` + 补 `」`，还顺手把 allow 推翻（2026-10-27 終遠のヴィルシュ -ErroRsalvation-）

**症状**：成品一行 73 字，是**全篇唯一**一行「`「` 不在行首」：

```
アドルフの瞳が据わる瞬間を目撃し、私は慌てて話を変えることにした。「て、手前の国立研究所までなら、何か理由をつければ」入れるかもしれないけれど――
```

**真相（源 `601.DAT` 7826–7836）**：

```
7826/7827  正文（旁白 2 段）
7828       0x1F4  ← 点击，框①到此结束
7831       voice / 7832 名札 #NAME[1]
7833/7834/7835  台词 3 段（其中 7834 已先关一次 」，7835 块末又关一次）
7836       0x1F4  ← 点击，框②到此结束
```

⇒ 正解**两行**。交付版把两框并成一行，并删掉块末的 `」`。
同批还有两处同源改写：`304.DAT` 7074 块内缺收尾 `」` 被**补上**；`501.DAT` 4157 原串 `かわいそう。かわいそう。` 被**删成一遍**。

**关键信号（第 3 次重复出现）**：`allow` 里 `#@open-quote` 登记的就是 `304.DAT` 那一行「块内本身无收尾引号」——
被"配平"之后，`allow` 与成品**对不上**。三次案件（もし神様 / 十三支演義 / 本作）都有这条信号。

**判据（照抄即可）**

1. 重跑 extractor → 与成品 `difflib` 逐行 diff：差异只剩「引号增删 / 跨框合并 / 同句少一遍」⇒ 必是后处理；
2. 回源看框界（`0x1F4` 等 wait 指令），别信成品的行；
3. 查 `allow`：成品某行与 allow 登记形态不一致 ⇒ 以 allow＋源为准；
4. 顺带做「行内自我重复」自检（`len%2==0 and s[:n//2]==s[n//2:]`）——本作靠它抓到 50 处**文本组多变体**被拼全（另一个独立缺陷，见 `S4-stcm2l.md`）。

**处置**：撤销后处理、恢复直出；源侧多/缺的引号逐行登记（`#@quote-surplus` / `#@open-quote`），**一个字都不改**。
