# 反例清单：看着像判据、其实会骗你的特征

> **用途**：判型 / 定界 / 解码时先扫一遍这一册。每条＝**误判特征 → 为什么会骗 → 正确做法**。
> 这里只收**跨作品成立**的反例；只对某作成立的写在 `WORKS-<族>.md` 的作品块里。
> 出处用「作名/日期」标注，便于回查原始证据。

## 一、字节宽度类（最致命，静默丢 20%+）

**1. 「读到一个像指令的字节就切」—— 汉字尾字节会撞指令码**
`0x76`/`0x77`/`0x7C`/`0x7E` 等既是结构符又可能是 SJIS 双字节字的**尾字节**（如 `学=8a77`）。
→ 主循环**必须先判首字节**（`0x81–0x9F` / `0xE0–0xFC` 吃 2 字节），再判结构符；否则整段错位。

**2. 「`0x7E` 当 1 字节没影响」**
把 `0x7E` 误当单字节会**静默丢 10%+ 文本**，且不报错。→ 宽度表按「首字节区间」写死，别按「常见字符」猜。

**3. 半角片假名不等于「坏字符」**
JIS X0201 的 `0xA1–0xDF` 在某些作里被**字体页映射成平假名**显示（遥か4）。→ 看到半角片假名不要直接判化け；
先确认该作的字体页映射，再决定是否转换。

## 二、长度 / 边界类

**4. 长度字段「对齐后相等」是不够的**
`A4(len(text)) == L` 会漏大量记录 —— 长度常**含尾部 NUL**，要 `A4(len+1)`。→ 用「双写长度」（`L/4` 与 `L` 成对）
互相校验，而不是单看一个字段。

**5. `idx` 不能用来回退找边界**
同一条消息的**分行片段 idx 会乱**（`0x535fc` idx=12、`0x53668` idx=8 实属同句）。→ 用 `node`（记录指针）判边界。

**6. `00 00` 不是消息分隔符**
并非每条消息都以 `00 00` 结尾。→ 用**记录头/长度**定界；`00 00` 只作辅助信号。

**7. 「没有 BOUND 标记 ⇒ 是续写」是错的**
无标记时按续写合并，会把**教程标题与正文**、**辞典相邻条目**粘连（曾把 247 条辞典粘成 1 条）。
→ 默认**新框**，只在看到明确的追加码时才合并。

**8. `first offset == 0` 不是「空条目」**
字符串池首条偏移可以为 0（相对 dataOffset）。→ 判空要用「长度=0 / 越界」，不能用偏移 0。

## 三、解码类

**9. 「解出来读得通」≠「字对」**
错字也能组成通顺句（如 `（`→`戊`、`しています` 的假象）。→ 用**引号配对 + 外部核对（vndb/官方）**验收，
不要以「读得顺」收工。

**10. 「这个字在别处正常出现过 ⇒ 它不是替换槽」—— 错**
同一个字可能**既有正常码位、也有替换槽码位**（`華`=0x02e0 ×47 与 0x0da4 ×57 并存）。
→ 只有「渲染出来直接读」能定槽位内容；**非标准码位先上报，不要静默删除**。

**11. 「自建字符集＝cp932 码序」只是初始假设**
必须用**真实台词逐区验证**，尤其**二级汉字区**（`0x989F–0xEAA4` 可能被私有排序）；
不做验证会把 800+ 行真实汉字当成「正确解码的稀有字」（或反之）。

**12. 图集字形的物理顺序 ≠ 码序**
位图字体按行/块排列，**字形顺序与游戏码无关**，不能拿图集当查表。→ 必须靠「已知码自证」建立 code→字形映射。

**13. 模板匹配 / OCR 小字形不可靠**
7×7 或 36px 字形做模板匹配/OCR 会错字（已实测多轮失败）。→ **只准人工目视单字**；批量建表禁。

**14. 字符似然模型会把「全角数字/指令字节」当假名**
这是**噪声主源之一**。→ 似然打分只作初筛，定论必须靠结构（记录形状/表）验证。

**15. 「grep 不到日文 ⇒ 没解密 / 不是文本」**
文本可能**全在 zlib/LZ 流里**（解压前 grep 0 命中）。→ 先按容器表解压，再搜；别因 0 命中换路线。

## 四、语义 / 结构类

**16. 宏不能「一个当一个用」**
`ff08` 是**一人称「私」**，不是主角名；`ffe6/ffe7` 才是姓/名。→ 宏按**句中的语法角色**判读（一人称 / 姓名 / 称呼）。

**17. `msgid` 会重复 → 不能按 id 建字典**
同一 msgid 可出现多次。→ 按**下标顺序**遍历；需要索引时用「文件+序号」。

**18. 归档里「同内容的第二份副本」不是索引**
常有「按解锁顺序重排」的副本，**不是 ID 顺序**，别用它定序（遥か系）。

**19. 字符串池的存储序 ≠ 显示序**
池常按 SJIS 排序（供二分查找）。→ 显示顺序必须由**独立的顺序表**决定（`scenelist.json`、事件表、调用图 DFS）。

**20. 「含控制符 ⇒ 整条丢弃」会静默漏文本**
某作扫描器用这条规则，**静默漏收 41%**。→ 控制符应**剥离后保留**文本，只有确认是系统串才丢。

**21. `FFFE` 后跟非字符（如 `FFE6`）不是「换框」**
误判会 flush，后半句被当人名段吞掉。→ 换框判据要「`FFFE` + 合法换框 op 序列」，不能只看第一个字。

**22. 启发式（含平假名）不能替代 op 判据**
按「是否含假名」分类，比按 op 判据**漏 100 处**（旁白→旁白段）。→ 结构判据优先，启发式只作兜底并标注。

## 五、方法论类（违反即无解）

**23. 枚举偏移 / 相似度打分器**
「起始偏移扫 0–1200、用浊点对相似度打分」曾整轮失败。→ 用**一条已知明文锚定基址**，不扫区间。

**24. 「多半是噪声」的版权串可能是密钥**
把「半可读的版权串」当噪声删掉，是致命误判 —— 密钥就藏在那里。→ 任何**半可读串**先记录再判断。

**25. 只追「已知的那个 op」⇒ 整类记录静默丢失（选项最常中招）**
看见 `68 …FF` 出正文就只扫 `68`，把"操作数整体能否解成日文"当扫描器 ——
`F6 01 00 FF <u16 idx> <u8 len> <文本>` 这种**前面带参数**的记录永远解不通，于是一条不剩地漏掉，
还会得出「本作无选项」的错误结论（ラスト・エスコート 深夜の黒蝶物語：漏 574 条 / 287 组）。
→ 新格式先做**全 op id 频次 + 每个 id 的载荷形态**盘点（`Counter(op)` + 每种 op 打 3 条样例 hex），
再决定扫哪些；闭壳校验（清空已知载荷后重扫残留日文串）残留非 0 就必须回头补扫。

**26. PACK 头里紧跟 `nameLen` 的那段，可能根本不是名字，是 XOR 密钥**
（アンジェリーク エトワール PS2 / Koei「PACK H2」，2026-10-18）
`'PACK' + u32 nameLen + byte[nameLen]` 里的 `byte[nameLen]`，看起来就是"文件名"（还"被编码了"），
于是花了整轮去猜"这是什么字符集/压缩"，全都失败。**它其实是密钥**：`data[i] ^= key[i % nameLen]`。
三个同时成立的信号（出现任意两个就该试 XOR，不要再猜编码）：
- 那段字节**几乎全部 ≥ 0x80**，且高位像"页号"（`0xd2 0xca 0xc1 0xd9 …` 交替）——像字符集编码，其实只是 XOR 后的表观；
- 同一族 PACK 里这段**长度不同**（24 / 32 / 40），而"文件名"不该有这种规律；
- 记录表 `+0x30`(off) / `+0x34`(stored) 读出来是天文数字（`0xd9c1cad2`）或恒定值 —— 字段本身没错，只是**整段被 XOR 过**。
**一步自检**：把那段当周期密钥 XOR 数据区，首 u32 若 **== 段长-4**（或 == 输出长度），即命中。
本作实测：XOR 后首 4 字节精确等于 `stored-4`，紧接着露出 `SCPT` 魔数 —— 一条判据定案。
→ 教训：**头里"看起来像字符串"的定长块，先按"可能是密钥/表"试一遍 XOR，成本 1 行代码。**

**27. 「同一引擎族 ⇒ 同一个 cmd 语义」**
Idea Factory STCM2L 同族 PSP 作里，`0xd2`/`0xd3` 的含义可以**正好反过来**：
`マイナスエイト` 是 `0xd2`=新框（点击）、`0xd3`=框内续行；`官能昔話 ポータブル` 则是 `0xd2`=续行、`0xd3`=框末点击
（2026-10-19）。按前作推定 ⇒ 全篇**并句**（台词框＋地の文粘成一行），且引号配对照样能过，肉眼很难发现。
→ 定档只认**本作统计**：取该 cmd 的记录，看**收尾形态**——`d2` 11,777 条**无一条以 `」` 收尾**、`d3` 95% 以 `」`/`。`/`）` 收尾，
一条统计即可定案（几分钟），比读 EBOOT 反汇编快。
