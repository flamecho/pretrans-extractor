# 结构判型与定框

> > **总览看 `pitfalls/A-decode.md`**；本文件只在「整脚本结构、要判记录类型 / 定『一次点击』边界」这一阶段读。

**「记录头字段」不必然是稳定类型 —— 判型别只认单个偏移；定框也别用「相邻 id 差」**

- **同作内不同文件、同一偏移可给不同值**，且**不同记录类共用同一值域**。
  实证（STCM2L **Switch**／BLACK WOLVES SAGA -Weiβ und Schwarz-）：正文记录的 `u32(i-0x1c)` 在 A 文件＝`0x66`、
  B 文件＝`0x64`；而 `0x62–0x78` 同时被资源名（`her01`）／`sureNN`／选项对象占用
  ⇒ 把该字段当「类型」会**同时漏收与错收**（我因此绕了数小时）。
- **判型用三重证据**：① **固定后缀签名**（结构位置，如 `u32(i-0x18)==0x61 & u32(i-0x10)==0x10 & u32(i-0x0c)==0 & u32(i-0x04)==1`）
  ＋ ② **值域**（同一偏移的取值分布，如 `0x4ba`＝正文 / `0x4bc`＝名札 / `>0x1000`（文件内指针）＝对象类）
  ＋ ③ **内容**。单字段取值只能当**辅助**。
- **定框（一次点击＝一行）优先找「显式终止记录」**，其特征是：**同一框内相邻正文之间绝不出现、框的末行之后必现一次**。
  ⚠ **不要用「相邻 id 差 == 1」当框边界**——框内 id 也会跳号（实证：同框两行 id 差 2）
  ⇒ 按 id 差定框会**静默并句/断句**，且行数与引号配对都可能仍然「看起来正常」。
- 顺带：终止记录**本身也占一个 id**，可用「终止记录 id ＝ 末行 id ＋ 常数」反向自校验框划分。

**「换框符优先于插入块」——别把 INS(名字插入) 当换框抑制器**

- 两种 gap 形态，结论相反，**只看有没有显式换框符**：
  ① `<显式换框符 BOUND/C7/M91> … <INS> <04 记录>` ⇒ **换框**。INS 的值绑到**后一条记录的开头**，
     但两句仍分属两个文本框（实证：`…決断ですね。` ＋ `1e8b052422`＋`1ec7094774` ＋ `1e cf 02 1e 0a` ＋
     `…どうして、ここに？` ⇒ 拆两行）。
  ② `CLOSE … <INS> <04 记录>`（gap **无**显式换框符） ⇒ **同框**（实证：`（` ＋ INS(`アンジェリーク`) ＋
     `さん気づいて…）` ⇒ 并一行）。
- **判据**：**BOUND/C7/M91 一旦出现即换框（与 INS 位置无关）；只有 CLOSE/INS 时不换框。**
  ⚠ 曾误用「gap 内最后一个分隔符在 INS 之前 ⇒ 不换框」，把形态①也判成同框
  ⇒ **相邻两个文本框被粘成一行**（症状：一行里出现两句、第二句以主角名/`（` 开头）。
- **自检探针**：① 行内出现 `。` 之后**紧接主角名**再接句子 ＝ 过度合并；
  ② 引号/括号配对计数 ＝ 括号类拆合信号。

**★★同一「记录槽位（scene＋lineNo）」可有多条同类记录 ── 引擎逐条执行、文本框「后写覆盖」⇒ 生效的是最后一条（Aromarie ATL 実証，2026-10-15）**

- **形态**：脚本表以 `(sceneId, lineNo)` 定位一行；同一 `lineNo` 可挂**多条**记录（`0`注记/`1`正文/`2`演出/`6`选项…）。
  引擎 SQL 会出现 `WHERE sceneId=? AND lineNo=? ORDER BY type,param`（**一次取该槽位全部记录**并按 type,param 升序执行），
  而文本命令是**写同一个文本框** ⇒ **后写覆盖**，玩家看到的是 **`param` 最大**的那条。
- **旁证手法（零成本）**：找一处「空文本记录 ＋ 有正文记录同槽」的例子 —— 游戏**能正常显示正文**
  ⇒ 证明是**后写覆盖**（若首写优先，玩家会看到一个**空文本框**，作者不可能出货）。
  实测：月ノ光太陽ノ影 本篇 `scene125 lineNo=0` ＝ 空 talk(`param 0`) ＋ 正文 talk(`param 11`)。
- **为什么会出现多家**：**作者改稿时编辑器追加新记录、而非覆盖旧记录**。FD《-Another Moon-》里 328 组同槽双行，
  其中 135 组是 (正文,正文)：改稿版 `talkId` **成批追加**在原 talk 之后（scene0 追加 187–192、scene23 追加 273–278），
  且语音表由 **`X<角色>NNNN`（旧録音）→ `Y<角色>NNNN+1`（新録音）** 成对出现 ⇒ **旧版／改稿版并存**。
  两版差异：120 组只是「字面默认名 `美希`」↔「宏 `%NA03%`」（代入默认名后同文）；**15 组是真改稿**
  （`行こう、美希`→`行こう。`／`美希みたいに`→`あんたみたいに`，改稿版改用代名詞）。
- **处置**：同槽同 type **取 `param` 最大者**，其余丢弃；**不处理 ⇒ 成片「相邻重复行」**（120 组），
  且会同时混入半句/改稿前旧文。⚠ 改完驱动**务必对上一作做 `cmp` 字节级回归**。
- **连带**：同一 talk 的 `phrase` 多段（`phrase=0,1,2…`）**必须先按序拼接再判句**——源里大量 `phrase=0` 是**半句**
  （如 `……ふう。`＋`またこのパターンかい？`＋`…戻ってくれないかな」`），漏拼＝丢文本＋**引号不配对假象**。

**★★同一引擎/同平台，记录框架可整体「多型」—— 用「节点头长 k」并扫 ＋「类型指针跨文件稳定」做全库聚合分类（STCM2L Switch 实证，2026-10-15）**

- **同一 STCM2L（Switch）下已实测 ≥3 种互不相同的记录框架**：猛獣＝`0x14058` 消息描述符；
  BLACK WOLVES＝`0x61` 串对象（判型见上「三重证据」）；**Glass Heart Princess＝「节点 3 型」**。
  ⇒ **换作必回查**，前作判据一律不照搬（与铁律「换作必回查 opcode/编码/换框」同源）。
- **节点 3 型**（尾恒 `[0][L/4][1][L][utf8][pad]`，`self` 指针恒指向尾的 `0`）—— 头长由 `k` 决定：

  | k | 头长 | 布局要旨 | 语义 |
  |---|---|---|---|
  | 1 | 44 B | `[1][REF][1][size][self][2.0][2.0]` | 正文 / 话者名 |
  | 2 | 56 B | `…[size][p1][2.0×2][p2][2.0×2]`，**`p2`＝节点末尾＝强校验** | 选项 / `switch` / `sureN` |
  | 3 | 32 B | `[0][1][1][4][KIND][0][L/4][1][L]`，其后**裸记录**续行 | 变体台词列表（一框多行） |
  ⇒ **并扫 k=1/2/3**（各自头长不同）。
- ★★**span ＝ 头长 ＋ L**（k=1：`44+L`；k=2：`56+L`；k=3：`36+L`）。
  **算错 4 字节 ⇒ 相邻节点全判「不连续」⇒ 整库不合并**（本例行数从应有 **21k 虚高到 33k**，且文本仍逐行可读）。
  与「别尽信长度字段」互补：这里是**自己算错 span**，症状是「行数虚高、同框被拆」。
- ★★**类型指针（REF/KIND）跨文件稳定 ⇒ 分类要「全库聚合」，别逐文件**：
  本例 正文 `0xE38C`／话者名 `0xEA88`／选项 `0xF6C4,F6F4,F700`（**个别文件整体 +0x30**，如 `100.DAT`）。
  逐文件分类时，正文极少的文件里某 REF 组只有 1–2 条 ⇒ 被 `MIN_GROUP` **误杀**。
  正解＝**先把全库同 `(k,REF)` 的记录聚到一起**，再按**组内「假名/汉字含有率」**判 `TEXT`（≥.75）/`NAME`（.10–.75）/`NOISE`；
  `k=2` 且含日文 ⇒ 选项；纯 ASCII 的 `k=2`（`色変化判定`・`ＢＧＭキュー`・`limit`・`file_count`…）⇒ 噪声。
- **框**（一次点击）＝**地址连续的节点串**（可含前置话者名节点）；**框分隔记录** `[0][0x1F4][0][0x10]`。
  续行/裸记录读取**遇节点起点即停**（否则跨框重读 ⇒ 同句双发，见 `pitfalls/B-lines.md` ㉖）。
- ⚠ **同句并存「宏版」与「字面名版」**（`「#Name[2]さん…` ↔ `「京子さん…`）＝不同分岐 ⇒ 按 SKILL.md §0 全保留，
  别当重复行删；若用户要求去重再处理。

**★★「tag/字段号」可能压根不是字段号，而是「载荷长度的冗余编码」—— 判型前先拿长度自证（千銃士R `SceneMasterVO`，2026-10-16）**

Unity（IL2CPP）系自研「VO 序列化」常见：

```
字符串字段 = [i32 描述符][u32 字符数][UTF-8 字节]
    描述符 = -(字节数 + 1)      ← 它只是字节长的同义反复，不含任何字段语义
数值字段 = [i32 >= 0]（自身即值，无载荷，扫描时自然跳过）
```

自证（**必须做，别跳**）：`マークス`(12B)→`-13`、`シャスポー`(15B)→`-16`、
`code_style_stories_001_0001_001`(31B)→`-32`、245B 长台词→`-246` —— 全库 100% 自洽。

- ⚠ **迷惑性极强**：本例描述符**值域恰好 255 个**、部分序列还呈**步长 3**，非常像「枚举型字段号」。
  我据此按 tag 分类 ⇒ **把 `code_*_stories_*` 场景 ID 与正文归进同一类**（同一个 tag 既是台词又是 ID，
  唯一度/distinct-ratio 统计全部失真），白绕一轮。
- **正解口径**：拿到「`[i32 X][u32 L][L 字节]`」形态时，**先算 `-X-1 == 实际字节数` 是否恒成立**；
  成立 ⇒ X 是长度、**字段语义只能靠位置**；不成立 ⇒ 才按字段号/类型去猜。
- **无标签序列化的位置语义怎么定**：本案记录语法实测为
  `[场景ID][flag][bg][bgm][名札][正文][unit_*]…[flag][voice]`，其中
  **名札 = 含假名/汉字的串 且 其「下一个字段」也是日文串**；
  **正文 = 含假名/汉字的串 且 其「下一个字段」不是日文串 且 不在名札词表内**。
  ⇒ **「后随同类串」＝名札位**这条零成本判据，把 1,337 条名札与 87,562 条正文一次分干净（误判仅 32 条复合名）。
- 配套：记录头 8B sentinel（本例 `29 00 ca 9a 3b 00 00 00`）+ 文件头 `u32 总记录数`；
  文件名 `*MasterVO.bin` 一族（`SceneMasterVO` / `WorkTalkScriptMasterVO` …）都是同一格式。
