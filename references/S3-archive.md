# 容器 / 归档 / 定长表（案例）

> 坑总览见 `pitfalls/A-decode.md`；本册按阶段查阅。
> 见 `S3-archive-family.md`。

**内联插入可能是「定长表引用」，别当成「文本内联」**
插入块解出来是空 / 断句时，先怀疑真值在一张**定长记录表**里（不是变量表缺失）。
- 表基址＝**「空槽字面」反推**：空槽（`仮`/`用語予約NNN`）暴露 **slot 索引 ≠ 逻辑 ID** 的错位；
  由空槽字面编号 N 推 `base = 槽地址 − N × 记录长`（遥か5：`0x1a5e0 − 368×64 = 0x149e0`）。直接 `base=0` 会整体错位、查到邻居值。
- 定位表本身：找**长度固定、首字段是可见语/读音**的密集区，用「首条已知语」（遥か5 首条 `御使い`）锚定。
- 表可能**一 leaf 内多张**（同 leaf 同时含 用语表 / 字表 / 章題表 / 年表），别只找一张就收工。

**同一作系的「本体」与「FD/续作」可能换插入机制 —— 每作必须重新求证**
遥か5 本体：正文插入走**两张定长表**（52B/64B）＋ `1e 05290204`/`1e 05b2027e`；
同作的 FD《風花記》则**完全没有表插值**（两指令计数 = 0），改为把用語/续写**直接写成内联 `04` 文本记录**
（前导 `02<id> + 1e 4e 04 3a 14` / `1e a6 04 a8 14`）⇒ 记录扫描+合并即得，**无需查表**。
→ 照搬本体代码会「找不到表」而断言失败；反之把内联当表则断句。**开工先数一次 TERMOP/GLOSSOP 计数**即可判定走哪条路。

**選択肢 op 与 调试菜单 op 可能是同一个 —— 结构分离不了，只能内容过滤**
風花記：選択肢 = `1e c6 02 87 06` / `1e 72 03 91 0b` 前导的 `04` 记录（正文流内、1 记录 1 条）。
但**デバッグ分岐メニュー也走同样的 op**（`〜の量は？` / `〜の場合` / `〜をセット` / `〜周目` / `見ますか？`）。
→ 别指望靠 opcode 区分；用内容剔除调试项，剩下的真选项按序收（这也符合「选项一行一条」）。

**見出し語/角色表锚定要「双重」—— 首条已知语可能在同一 leaf 出现多次**
風花記母表：`桐生 瞬` 在同一 leaf 内出现 **2** 次（0x65f1 的另一张表区 + 0x167cc 的真見出し語表）。
只按「首条已知语」取第一处会**锚到错的表**（stride、字段全乱）。
→ 追加第二个锚：要求「+stride 处正好是第 2 条已知语」（如 `+64B == 坂本龍馬`）才认。

**同一场景可能同时存在「旧稿 leaf」与「冒頭修正版小 leaf」—— 两个都当独立场景就会重复＋显示旧稿**
風花記：序章冒頭在 2 leaf —— `leaf 18`（本編 126 記録，冒頭 `今度は…誰？`）と `leaf 4999`（9 記録，
冒頭 `…誰か私を呼んでる。これは…？`）。修正版 `4999` **末尾で入口ラベル `イベント・共通序章頭` を宣言** ⇒ 実機はこちら。
→ 見分け方（自動判定可、誤検出 0）：① 同タイトル（先頭記録一致）② 冒頭が**逐条対応**（小 leaf 末尾のラベル連続を除いた
n 条が大 leaf 先頭 n 条と**位置対応**、n−2 条以上一致かつ 1 条以上相違）③ 小 leaf 末尾にラベル宣言 ⇒ **overlay**：
大 leaf の対応冒頭を差し替え、小 leaf 単体は出力しない。
- ⚠ 同タイトル leaf 対は 100 対以上あるが**大半は別内容（別分岐/別場面）**。位置対応＋高一致率で絞れば誤検出しない。
- ⚠ 見落とすと「同じ冒頭が 2 回、初出が旧稿」になり、実機と突き合わせて必ず気づかれる。
- 修正版 leaf は**冒頭だけ**のことが多い ⇒ 大 leaf の**本文は捨てない**（叙述接続＝別 leaf へ続くかで確認）。

**★ 归档条目表的高位 ＝ 压缩标志；「能读到明文片段」≠「未压缩」（裏語 薄桜鬼 PSP，Zerodiv 自研）**

条目表 `{u32 size | 0x80000000, u32 size2, u32 offset}`：
- **bit31 ＝ 压缩标志**（1＝压缩）；`size` ＝ 压缩后字节数；**`size2` ＝ 解压后字节数**。
- 自检：`Σsize ≈` 文件数据区（实证）；**`size2/size` 稳定 ≈2~3 ⇒ 几乎必是压缩**。
- **误区**：LZ 的**字面量本身就是明文** ⇒ 只看"能读出通顺句子"就判「未压缩」会**漏掉约 3/4 文本**
  （旧案：20 万字 → 实为 80 万字；且"缺字"现象会被误解释为"词表引用/文本不落盘"）。
- 解压器在 EBOOT：`init` / **`decode`** / `fini` 三件套（由「读条目」函数按 bit31 分派：未压缩直接 `memcpy`）。
- 本例为 **LZO1X-1**（miniLZO）。识别特征：`m_pos = op-1-((t>>2)&7)-(*ip<<3)`（M2）、
  `m_pos = op-((t&8)<<11)-((ip[0]>>2)+(ip[1]<<6))`（M4，含 `-0x4000`）、first_literal_run 的 `op-0x801`、
  match_done 的 `t = ip[-2] & 3`、字面量首字节 ≥0x12 ⇒ 长度 `b-0x11`。移植：`scripts/lzo1x.py`。
- 验证锚：解压后长度**必须等于 `size2`**（命中率 100% 才算对）。
- 伴随坑：文本 data 以 `00 00` 收尾并**对齐填充到 4 字节**（常为 4 个 `00`）⇒ 取文本用
  `d.split(b'\x00')[0]`，**勿用 `d[:-2]`**（残留 NUL ⇒ 整块被"含控制符"判据丢弃）。
  仅含标点的续行（如 `　…………？」`）须**放行日文标点**，否则会被"含日文"判据误弃并造成引号不配对。

**★ 同一句在脚本里并排存多版（台詞バリアント機構）—— 别当提取重复删（裏語 薄桜鬼 PSP，Zerodiv 自研，2026-10-14）**

线性扫描会把这些变体**全部取出**（本作 1,594 行 = 4.8%），看起来像"重复行"，实为引擎内建机制。

**判据（三条齐了才定性）**：
1. 两版是**各自独立的文本指令块**（各有自己的 pos，不是同一块被扫两次）；
2. 两版之间夹**零长度 marker** —— 本作 `0x1e`（928 对近重复中 **77%** 由它分隔），
   外层 `0x1c`（組開始）→ `0x1e`（区切り）→ `0x1f`（終了），有时 `0x2a`（改ページ）夹中间；
   典型帧（entry0 @0x2b0c）：`0x105{idx,"chara_02_1.enc"}` → `0x1c` → `[0x2d 名][0xb6][0x2f…]` →
   `0x31` → `0x1e` → `[0x2d 名][0xb6][0x2f…]` → `0x31` → `0x1f` → `0x2b`；
3. 两版**各带自己的台詞ID与参数**（本作 `0x31` 为连番台詞ID，人名后 `0xb6` 8 B 值也连番）
   ⇒ 引擎把它们登记为**两条独立台詞**（这也是"是不是重复"的最终判据：参数各自的 ⇒ 独立登记）。

**变体差异**（928 对，已排除立绘指令块）：完全相同 15 / **仅称呼差异 532** / 称呼+少量改写 160 / **内容不同（真分岐）221**。
A 版＝**名前ベタ書き**（`梢`/`霧島梢`）＋漢字表記；B 版＝`&pcl` 宏 / 代名詞・関係語（彼女・あいつ・妹・妹よ・あなた・君・お前・こいつ）＋ひらがな表記（`来ます`↔`きます`）；也有整段删名（`落ち着け、梢`↔`落ち着け`）。
推断（**未确证**）：A/B ≈「音声に入っている名前を読む版 ↔ 名前を言わない版」，`0xb6` 疑为 `{キャラID, ボイス番号}`；
验证被阻：语音库 `sound/btlvoice.awb` 是 **CRILAYLA 压缩**（头非 `AFS2`）⇒ 无法用 AWB 条目数比对，**勿据此断言**。

**处置**：把主角名归一（`&pcl`→默认名）后**逐字全同**的才去重（本作 427 对/854 行）；**内容真不同的必留**。
⚠ 不要用「相邻重复行」一刀切，也不要在未问用户前动产物（SKILL.md §0 不改写原文）。

**补注（2026-10-15，Aromarie「ATL」的同族机制已**确证**，可作上例的机理参考）**：
月ノ光太陽ノ影 FD《-Another Moon-》的 `line` 表同一 `(sceneId,lineNo)` 挂着**两条正文记录**＝旧版／改稿版并存，
改稿版 `talkId` 成批追加在原 talk 之后，**语音表也成对**（`X<角色>NNNN` 旧録音 → `Y<角色>NNNN+1` 新録音）。
引擎 SQL `… WHERE sceneId=? AND lineNo=? ORDER BY type,param` **逐条执行**、文本框**后写覆盖** ⇒ **显示的是 param 最大者**。
**旁证**：同表另有一处「空正文记录(param 0) ＋ 正文记录(param 11)」同槽且游戏正常显示 ⇒ 非首写优先。
两版差异分布也一致：120 组只是「字面默认名 ↔ 宏 `%NA03%`」（代入默认名后同文），15 组是真改稿（改用代名詞／删名）。
⇒ 上例「A/B 双版」不必假设靠语音内容区分；**更可能是「编辑器追加的改稿版」，引擎取后者**。
⚠ 但**引擎不同不可直接移植结论**：裏語的 `0xb6` 语义、以及「是否也用後写覆盖」仍未确证（细节见 `S6-typing.md`）。

## ★ CRI CPK「无 TOC」情形：偏移只能靠累积推（2026-10-19 うたプリ All Star）

- 判据：`@UTF` 头里 **`EnableFileName=0` ＋ `TocOffset=0/TocSize=0`**，只有 `ItocOffset/ItocSize`。
  ITOC 行只有 `ID/FileSize/ExtractSize`（无文件名、无 per-file offset），且常拆成 `CpkItocL`＋`CpkItocH` 两张子表。
- 偏移推算：两张子表合并 → **按 ID 升序** → 从 `ContentOffset` 起按 **`Align`（本作 2048）累加 `FileSize`**。
- **唯一硬校验**：`Σ align(FileSize) == header.ContentSize`（本作 230,252,544 精确相等）。
  只有等式成立才证明顺序对；差值>0 就是顺序错或漏了子表。
- 若某行 `FileSize != ExtractSize` ⇒ 该成员是 CRILAYLA，按 `ExtractSize` 读取后解压（`cpk.py` 已有实现）。
