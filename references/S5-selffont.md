# 自建位图字体（字形图集）

> 适用：**引擎自建字符集**类作品（正文 = u16「游戏码」，非 cp932）。当低码区能靠 cp932 序对上、
> 高码区却「像汉字但读不通」时，**不要再逐位置猜** —— 去把它**自带的字体图集**找出来。
> 实例：STORM LOVER V（PSV, PCSG00735）。
> 名字宏 / 名字表 / 交付改名见 `S5-names-macro.md`。

---

## 1. 判据：资源里哪个文件是「字形图集」

依次验四条（**全部便宜、分钟级**）：

1. **值直方图**：字节值由 `0x11 / 0xff / 0xaa / 0x33 / 0x00` 之类**「高半字节==低半字节」**的值主导
   ⇒ 该数据是 **4bpp 打包位图**（相邻像素相近，两像素落在同一字节）。
   ⚠ 随机/压缩数据该比例≈6%；带零填充的假阳性要扣掉零基线再看。
2. **行宽**：对 4bpp 展开后的字节做自相关，**峰值位置 = 每行字节数**（本文实例 = 18B = 36px）。
   邻位（±1）也高 = 图像平滑，属正常。
3. **字形高**：按 `行宽` 渲染成 1px 宽的长条，算**每行墨量**再做自相关，**峰值 = 字形高**（实例 = 36 行）。
4. **渲染验证**：`字形索引 == 游戏码`（从 0 起），拿**已知码**渲染验证 ——
   `CHARSET.index('あ')` 渲染出来必须是「あ」。这是**一比一**的自证，不成立就换索引假设。

由此得：**cell = 行宽 × 字形高**（实例 18×36 = 648B/字形）；文件能被 cell 整除的部分 = 覆盖的码数
（实例 2,324,480 / 648 = 3587 ⇒ 该作字符集**只有 3587 个码**：低区 cp932 序 + 高区自定序追加字）。

## 1.5 ★ 码位不在字体码表里 ⇒ 是「控制码」，不是字符
自带字体的**码表**查不到该码 ⇒ 引擎渲染不出 ⇒ 必为**内联控制码**（cp932 解出的 `㌔`/`⑱` 纯属巧合）。
判「框内演出码 vs 换框码」：① 与 `\n` **并存** ⇒ 非换框；② 在**右括号之前**（`…うれしい[码]）`）⇒ 框内。
★**反证**：当换框拆行 ⇒ 产**孤立 `）`/`」` 行** ⇒ 用**引号配对**反证（实测踩过 36 处）。
AK ルトゥール `0x8760/875f/8751` 整段缺字形 ⇒ 判框内演出码，删后括号全配对。

## 2. 顺序陷阱

- 高码区（≥ 某边界）常是**游戏自定序**，**不是 cp932/JIS/Unicode 序**；
  别假设「码表 = cp932 原序」，也别拿「低码区=cp932」外推到高码区。
- **「字形索引==码」只保证认得出图**，不保证「游戏码==该字在 cp932 的码」。二者是两回事。
- ★ **同系列续作的自定序槽「逐作独立」** —— 前作的 SPECIAL 表**不可沿用**。
  实例：STORM LOVER V 与 2nd V（同引擎、同 `lt.bin` 规格）高码区槽序**完全不同**。换作必**重读该作字形**重定。
- ★★ **「槽序 == cp932 码序」是「逐作可判的约束」——先自检，再决定用法**（2026-10-12 细化）：
  1. **自检（几分钟）**：拿该作**已能文脉定/字形定**的槽，两两相邻校验是否**严格单调**。
  2. **严格成立** ⇒ 它是**候选窗口压缩器**（实例：プリンス・オブ・ストライド PSV，**57 槽 57/57 严格单调**）：
     未知槽的值**必夹在相邻两个已知槽之间** ⇒ 先把每个未知槽压到 **2–5 个候选**，再据字形/文脉挑。
     **效率极高（实例 57 槽秒级定完，零枚举、零 OCR）** —— 未定字前**先用此法**，别急着逐槽渲染猜。
     ⚠ 它**仍不是定值依据**（窗口内最终必须由**字形＋文脉**裁决），只是把搜索面从「整区」压到「几个」。
     锚槽优先取**文脉可判**者（本作 `完璧`/`俯瞰`/`腑抜け`/`騙される`），中间槽即被夹死。
  3. **不成立**（实例：STORM LOVER 2nd V，169 槽中约 40 处违例）⇒ 降级为**纠错提示**
     （用已定槽反查误判），**不得**用于窗口压缩，退回逐槽渲染＋台词仲裁。
  ⚠ 判「是否单调」必须用**已定槽**；拿未定槽去比是循环论证。
- ⚠ **字体字形可能被「重绘」** ⇒ 别拿「基础区同字字形**逐字节比对**」来认槽
  （实例 2ndV：`font[3456]('―') ≠ font[CHARSET.index('―')]`）。该法只在 kana/汉字**大区**的等值渲染自证时可靠。

## 3. 落地做法（比逐位置猜快一个量级）

1. 写一个 `glyph(code) -> PIL.Image` 的小工具（cell 定值 + 4bpp 展开），**渲染成表**目视。
2. 高码区**逐区渲染 + 真实台词上下文仲裁**定值，写进 SPECIAL 表后重跑。
3. ★★ **36px 字形人工辨字仍会错**（实例：把 `餃` 读成 `馥`、`闊` 读成 `閹`）⇒
   **有上下文的一律以真实台词为准**（`餃子` / `迂闊` / `軋み` / `太棹` / `叶えて`），
   字形只用于「上下文中性、无从判读」的槽。
4. 渲染时把「段尾未知槽」剔掉（邮件签尾图标等），能一次砍掉大量噪声行。
5. ★ **行尾装饰槽会自然消失**：实现常在取文本 run 时**裁掉行尾 ≥LEVEL2_START 槽** ⇒ 句尾装饰/图标**无需另设规则**
   （`勉強中Ⅵ`→`勉強中`），**只有句中**装饰才需 `fix_deco()`。⚠ 该裁剪**不分装饰/真实字槽** ——
  真实汉字槽若落行尾会被静默裁掉；自查「run 末槽 ∈ 二级区且 SPECIAL 为汉字」是否在正文（实测 0 例，全在被过滤的 UI 表）。

## 3.5 ★ 高码槽 ≠ 字符：可能是「语义标记／装饰绘文字」

字形是圈数字/罗马数字/图标，**文脉却明显当「词」用** ⇒ 它不是那个字形，而是**装饰绘文字／符号标记**。
实例（2ndV）：`専用の[Ⅳ]買って`（Ⅳ 实义=**携帯**）、`急に[Ⅷ]降って`（Ⅷ=**雨**）。

**判据**：同一封邮件/同一段里 `⑪` 与 `①` 混用 ⇒ 这组是**通用句间分隔、无固定所指**（不能硬塞词）。

**按文脉落地**：
- **对象类**（有明确所指）→ 改写为**实词**（`Ⅲ=メール / Ⅳ=携帯 / Ⅷ=雨`）。
- ★ **近义复现即丢弃**：同小句（~12 字）内**已出现该词或其近义**（メール/メアド、携帯/電話/スマホ/ケータイ、雨）
  ⇒ 只是**重复强调**，**直接删**；否则产 `メール[Ⅲ]と電話[Ⅳ]`→`メール**メール**と電話**携帯**` 式重复。
- **分隔类**（①..⑳ / Ⅴ / Ⅹ 等）→ 按句读落 **「。」**；前接 `？！。…、」』）` 时**不再补**。

**实现**：装饰词/分隔集**不要写进 `SPECIAL`**（与正文同词无法区分、去重失效）；
另设 `DECO_SEP`/`DECO_WORD` + 输出层 `fix_deco()`（见 `scripts/stormlover2_{charset,run}.py`）。

★★ **同一装饰槽在不同作可不同用法 ⇒ 归类须按「该作自己的全部用例」定，禁跨作照搬。**
实例：PSV 版 `Ⅷ`＝对象类（雨），同系列 PSP《夏恋!!》同槽 4 例**全为句尾装饰**（`…はいていませんでした[Ⅷ]水着を着たり…`）
⇒ 照搬会产 `…でした雨水着を…` 式错句；该作改判 `DECO_WORD={}`、整区按**分隔类**落地。
**做法**：装饰槽通常仅几十次 ⇒ 一次列出该槽在**本作的全部用例**（带前后 1–2 框）再归类；
**对象类依据必须是本作自己的 `[槽]ください` 型搭配**。固定在**行首**的 UI 记号（`㊤/㊦`）无需单列规则，行首记号剥离自会剔除。

**报告口径**：写清依据（原始字形＋文脉）＋**置空即可还原**；跨作差异单独列表（同槽异用＋本作用例）。
