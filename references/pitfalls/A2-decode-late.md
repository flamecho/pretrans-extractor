# A2 · 解码层（后期条目 ㉒〜㉗）

㉒ ★★**「未压缩」不能靠"能读到明文片段"下结论 —— LZ 的字面量本身就是明文**（2026-10-14，裏語 薄桜鬼）。
  条目表 `{size|0x80000000, size2, offset}` 的 **bit31 ＝ 压缩标志**、**`size2` ＝ 解压后大小**；
  旧版本据"明文可读"判「未压缩」⇒ 只拿到约 1/4 文本（旧 20 万字，实为 80 万字）。
  ⇒ **见 `size2/size` 稳定 ≈2~3 即按压缩处理**；解压器＝EBOOT 里的 `init/decode/fini` 三件套。
  本作＝ **LZO1X-1**（特征：`op-1-((t>>2)&7)-(*ip<<3)`、M4 的 `-0x4000`、first_literal_run 的 `op-0x801`、`t=ip[-2]&3`）；
  移植 `scripts/lzo1x.py`（01/`03-archive.md`）。
㉓ ★★**同引擎不同作品的 opcode 表会「整体平移」—— 不可照搬上一作的编号**（2026-10-14，裏語 薄桜鬼 → ～暁の調べ～）。
  实测：台词/选项/人名/无说话人文框/字库 **五者一致 +5**（`0x2f→0x34`、`0x21→0x26`、`0x2d→0x32`、`0x2e→0x33`、`0x31/0x20→0x36/0x25`）
  ＝ 枚举表前部多了 5 项。
  **判别法（不靠猜，四问定表）**：① 哪个 cmd 承载**长日文句**＝台词 ② 哪个**成组出现**（连续 2–6 个）＝选项
  ③ 哪个内容是**单字**＝字库 ④ 哪个块紧跟「名札」后＝人名。⚠ 直接用旧表 ⇒ 文本块一个都取不到（数量级掉到 1/10）。
  **同族既有坑**：`03-archive-delta.md` A17（STCM2L 的 opcode **逐文件** Δ 平移）—— 与本条（**逐作品**整体平移）合看＝「opcode 编号一律不可当普适常量」。
  实现＝把 opcode 表做成按作品名索引的 dict（`scripts/urakata_extract.py` 的 `OPCODES`），**改表不改逻辑**；
  ⚠ 改完驱动务必对**上一作做字节级回归**（sha 一致）再交付（`03-archive.md`/`04-lines-cases.md` B27＋B29）。
㉔ ★「**先查主数据文件是不是明文 SQLite**（头 `SQLite format 3`）」——命中即**零解密、零逆向**：

㉖ ★★**用語辞典/豆知識可能嵌在 assembly（`Assembly-CSharp.dll` 等）的 .NET `#US` 字符串堆里 —— 不是 TextAsset**（2026-10-15）。
  本作 Unity 包的 StreamingAssets/resources.assets 里查不到「辞書」，`grep` 全树只有 DLL 命中 ⇒
  **去 parse PE → CLI header → metadata root → `#US` 流**（堆格式＝`[compressed len][UTF-16][1 flag]` 连续）。
  堆内记录 = **`[読み][見出し語][解説]` 三元组连续排布**（解説含 `<br>`），ID 串另置堆中。
  **锚定法（免猜、免枚举）**：拿**脚本里已有的引用**（本作 `<tips name="HM辞書NNN">見出し語</tips>`）当钥匙，
  用「見出し語」回堆里定位三元组 ⇒ HM/SM/DC **329/329**；无引用的 `Z辞書` 用「ID 紧邻三元组」回收 131/147。
  ⚠ **同一个堆里常混其它标题的遗留串**（本作另有 `辞書001–219`＝江戸/天下五剣系、`回想NNN`＝别作回想一覧）
  ⇒ **判据＝「该词在本作脚本里 0 命中」**，整体排除（对齐铁律 12）。
  ⚠ 字符串**去重**会让三元组缺项（同一 `見出し語/解説` 只出现一次）⇒ 允许 3/2/1 元组，缺项用脚本侧引用补。
  ⚠ 堆内容≠IL 可用：本作**解说串没有任何 `ldstr` 引用**（IL 疑似被保护），但**堆顺序仍可用**；
  另 `ldstr` 的 token 指向**长度前缀**（`token = 数据偏移 − 1`），按数据偏移找会 0 命中（`03-archive.md` ／ `02-unity.md`）。

㉗ ★**「大小前缀＋LZSS」类自研压缩的变体同定：别枚举参数，用「≥MB 级文件」当判别器**（2026-10-15，明治活劇 ハイカラ流星組）。
  小文件（几 KB）常「**碰巧**长度吻合＋流刚好耗尽」⇒ 4KB 文件能同时通过 6 组错误变体；
  换 **2.27MB 的 `DEBUG.lzs`** 后只剩唯一解。判据＝**输出长ぴったり ＋ 输入全消费**（两条件同时）。
  ★★ **环起点 `r0 = N − F`（Okumura 传统，N=4096 则 0xFEE）必须列为候选**：r0 误取 0 时，
  「**绝对环索引**」会伪装成「**距离 = off − 1**」——**长度照样吻合，只有数%的字化け**（读得通、查不出）。
  实例：`len=(b1&0x0F)+3`／`off=b0|((b1&0xF0)<<4)`／フラグ **LSB-first・1=字面量**／`[b0][b1]` **字节互换**的 Okumura 变种。
  判定辅助：同一引擎的**大文件**（数 MB〜百 MB）能一次「全消费」＝变体对；小文件不算数（`03-archive-family.md`）。

㉘ ★★**`hactool --pfs0dir` 对 >1.7GB 的成员会写全零**（2026-10-15，ときメモGS2 NS）。
  NSP 里的 Program NCA（4.27GB）抽出来后**从 ≈0x65DD1999（1.7GB）起整段 0**，
  于是 `-t nca` 报 **`Invalid NCA header!`**（cnmt）／**`section 0/1 is corrupted!`** —— **全是假故障**
  （源 NSP 该处非零，已逐偏移比对证实）。小文件（cnmt/tik/cert）**同样被写 0**。
  ⇒ **NCA 一律自己用 Python 按 PFS0 表逐块拷贝**（`f.read(1<<24)` 循环），再喂 hactool。
  ★ 同类：**`--titlekey` 收的是「加密」titlekey**（＝`.tik[0x180:0x190]` 原值），
  hactool 会自行用 titlekek 解并打印 `Titlekey (Encrypted)/(Decrypted) (From CLI)`；
  **传明文会再解一次 ⇒ 全错**（现象＝各候选键全试也不通）。

㉙ ★★**自研「字符串池 XOR 键随池内偏移变化」**（2026-10-15，ときメモGS2 NS，KONAMI Unity `.bytes`）。
  `K(off) = 0x3C ^ ((off & 0xC0) | (off & 0x03))`（off＝条目在池内起始偏移）；**同条目内 K 恒定**、跨条目变。
  ⇒ 症状＝「同一文件里有些串用 0x3C 解得出、有些要 0x3F/0xBF/0xFC…」，易误判为「每串一密/流密码」。
  **★ 且解码出的 `0x00` 须还原为 `K`**：`（`/`？`/`好`/`何` 等**中间或末位字节 0xBC/0xBD** 被编码器
  写成 `0x00`（规避 raw=0 撞分隔符）；不还原会生出 `ｈ`(EF BD 88)、`！`→`ａ` 之类假字，
  且**引号/括号计数会失衡**。定键法＝「对每条试 256 键，取唯一使结果成为合法日文者」再拟合（本作 217/218）。
  细节 `02-unity-bytes.md`。

㉚ ★**Unity 自研 `.bytes`（KONAMI ADV）的块语义与选项判别**（2026-10-15，ときメモGS2 NS）。
  `[28B 头][4B 指令 <u8 A><u8 B><u16 BE>][字符串池]`；指令 **`05 03 <u16>`＝引用池**；
  消息块 `0316…0317`，**块后 `0402` 再跟 `01 04` ⇒ 选项块**（0503 全是选项；无说话人名），
  否则＝**名札＋正文**（第 1 个 0503＝人名，第 2 个＝正文）。
  ⚠ **两者骨架完全相同**，只能靠 `01 04` 判 —— 用「第 1 个是不是人名」判会把「要不要邀请」类选项吃掉。
  细节 `02-unity-bytes.md`。

㉛ ★**Takuyo gss `SCR 2.00` 的行内 op 补遗**（2026-10-16，ソラ*ユメ）：
  `0x108`＝**槽←串**（本例唯一用处＝`PRG_ROUTE` 写默认名 `皐月`；**别当文本收**）、`0x106`＝**清槽**、
  `0x10c`＝**sprintf→槽**（组装名札 `FullName`，剔）、
  `0x3a`＝**OR**（链式折叠＝「多旗任一」；判据＝`COM050` 四重 `0x3a` 折叠。据此 `COM049` 的 `d803|c808`
  在正常 play 由故事旗成立 ⇒ 其 25 行**保留**，别当 debug 一起剔）、
  `0x22`＝**条件为假则跳**（`0x23` 为标号 ⇒ `0x22..0x23` 之间＝条件为真时执行）。
  ★**`0xf0` 章题里可出现「文本宏」**：`【妄想家　@GameFirst】` 的 `@GameFirst`＝姓槽
  （同 カエル畑 `@GameLast`）—— `0xf0` 只有 1 个串操作数、**无槽操作数**，故作者改用文本宏；同类一律补 `NAME_MACROS`。
  ★**别把「版本串后紧跟的 u32」当版本后缀**：`SCR 2.00` 后的 `42 00 00 00` 是 **u32 A=0x42**，
  误读成 `SCR 2.00B` 会去找不存在的「B 版格式」。
- ★ **反过来也成立：版本串不同 ≠ 格式不同**。Takuyo `SCR 1.10`（Little Aid PSP）与 `SCR 2.00` 经**逐字节 diff**
  只差版本串本身，指令编码同构 ⇒ **不必另写解析器**（同族先 diff 再决定，别按版本号推翻重做）。

㉜ ★★**「同捆源脚本 `.txt` ＋ 编译体」双出货 ⇒ 先验「源未过期」再决定路线**（2026-10-16，新宿羅生門）。
  有些引擎把**源脚本**（SJIS 纯文本 `@命令`）与**编译体**（自研 `ASB` 等）**一起打进 RomFS** ⇒ **别默认去逆字节码**：
  先用**零成本一致性判据** ——「**编译体头部的语句数 ≈ 源脚本语句数**（±0.5%）」。实例：`.asb` 头第 3 个 `u32BE`(语句数) ↔
  `.txt` 计数逐文件吻合（`001/s00` 4871↔4861，全库 180 文件）；另证 `main`(NSO) 内含 `.asb` 字串（运行时确实读编译体）
  ⇒ 二者同源 ⇒ **以 `.txt` 为权威源**（§㉙ 的另一变体）。⚠ 别把源脚本当调试残留排除；也**别因编译体里搜不到明文就以为被加密**
  （本作 `.asb` 无任何 raw 日文串）。
  ★★**同法识破「出货即占位」**：副线剧本可能整块是 `テストシナリオ`，此时**编译体尺寸同样极小**（2 KB）
  ⇒ **「源未过期」与「数据本就如此」是两件事**，须逐文件分开证伪（比计数 ＋ 采样内容），否则误判为「源过期，该逆编译体」。
