# E2 · CRI CPK 块流／CRILAYLA／KAG `.ks`

## ⓐ ★CPK 数据区可能是「串接流按 2048 切块」，而不是「一条目一块」

**判据（3 秒、零成本）**：TOC 每行取 `FileOffset` 处 8 B，
若 `CRILAYLA` 且 **`FileSize == 16+csize+0x100` 且 `ExtractSize == usize+0x100`** ⇒
「条目＝块＝文件」成立；**命中率不是 100%**（本作 1,122/1,122，但仅 2,533 条目中的一部分有这层关系）
⇒ 仍需内容锚定。

- 本作真相：数据区是**所有文件首尾相接的一条逻辑流**，再按 **2048 B** 切成 4,399 块；
  每块独立「CRILAYLA 压缩 or 原样」。**一个块里可以出现多个文件的头**，
  文件边界与块边界**无关**。⇒ 按条目解包只能拿到 42%。
- **流还原**：`o = ContentOffset`；`CRILAYLA` 块 → 解码后 `o += align2048(16+csize+0x100)`；
  否则 `o += 2048` 原样取。拼接即逻辑流（本作 125 MB）。
- **切文件**：每个 `.ks` 首行是 `; <name>.ks`，**其前可能是 `\r\n` 或 `\x00` 对齐填充**
  ⇒ 正则须写 `(?:^|(?<=[\r\n\x00])); ([A-Za-z0-9_\-]+\.ks)\r?\n`，
  锚死 `^` 会漏掉三分之一（本作 1,403 → 2,527）。
  另有 `; name.ks-既読外伝タグ付け` 这类**注释式首行**，只认 `^\w+\.ks$` 会漏。

## ⓑ ★CRILAYLA 两处变体（标准实现会"看起来快好了"却中途崩）

1. **头 `u32@8` 是不含 `0x100` 原样前缀的明文长度** ⇒ 总长 `usize + 0x100`。
   按「`usize` 即总长」会尾部越界。
2. **count 是变长编码**：`2 bit`；若 `==3` 再读 `3 bit`；若 `==7` 再读 `5 bit`；
   若 `==31` 则 `8 bit` 循环（`0xFF` 续）。**按固定 `8 bit` 读会在中途耗尽码流**。
   ⇒ 症状极具欺骗性：**已解出的那一段文本完全正确**（因为反向解码从文件尾开始），
   随后 `dp+off >= len(out)` 或 `sp<0`，很容易误判为「块被截断 / csize 偏小」。
   正解＝参考实现 `Kuriimu2 …/Kompression/Decoder/CrilaylaDecoder.cs`
   （`ReadLength` 阶梯 + `ReverseStream` + `RawSize_=0x100`）。

## ⓒ ★TOC 的 `FileOffset` 可能与行错位一行 —— 只信内容不信列

本作 `rows[i].FileOffset` 指向**上一文件的块**，文件 i 的块在 `rows[i+1].FileOffset`。
判据：用上面的 `FileSize/ExtractSize` 等式逐行验，错位时 0 命中、下移一行后 100% 命中。
更稳的做法：**按块解码后用块内首行 `; name.ks` 定身份**（块内注释与 `[next file]` 链自洽），
TOC 名只在块内无注释时兜底。

## ⓓ KAG 式 `.ks`（自定义 KAG，cp932 / CRLF）成行要点

- 正文＝`[message …]…[/message]`（**一块＝一次点击＝一行**）；块内 `[br]` 是**软换行 ⇒ 合并**。
- 选项＝`[selectb word="…" file="…"]`，一行一条，**按文档序插在正文流里**。
- 需剥离：`[br]`、`[f size="30"]`/`[/f]`、`[se1|se2|se …]`；人名宏 **`[familyname]`／`[firstname]`**（绝不可丢）。
- **顺序**：`[next file]` 链常常**碎片化**（本作 1,361 段无入边），按链 DFS 会串到章中
  ⇒ 改用「族前缀（序章→路线序→`love_*`→`omake_*`→`bangai_*`→`end_*`）＋ 文件名」，
  文件名 `love_<角色><章>_<节>` 本身即阅读序。
- **旁白里的「讳」**：本作旁白 577 处「正成様」＝服部半蔵の讳（服部正成），
  **不是化け也不是错字**；名札表（`name_*.png`）里不会出现 ⇒ 别急着"修字"。
